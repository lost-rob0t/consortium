* External evidence (Brave, 2026-09-20)

** gptel (gptel.org, NonGNU-devel ELPA, accessed 2026-09-20)

- Async, streaming LLM client for Emacs; many providers plus any
  OpenAI-compatible endpoint; responses in Org/Markdown.
- *Tool use*: =gptel-make-tool= defines Elisp tools; results are fed back to
  the model — the documented agentic loop.
- *MCP*: client integration via =mcp.el= (lizqwerscott/mcp.el).
- *Presets*: bundle model/backend/system message/tools as a named preset,
  applyable from the transient menu or via =@preset-name= cookies.
- *Programmatic API*: =gptel-request= and =gptel-fsm= for custom flows.
- *Org integration*: =gptel-org-set-properties= (per-heading reproducible
  settings), =gptel-org-branching-context= (outline path = conversation
  branch), =gptel-org-set-topic=.
- Context management: buffers/regions/files/dirs via =gptel-add=.

** Agentic ecosystem on gptel (r/emacs "State of agentic coding in Emacs,
2026", 2026-07-15)

- Community consensus: the gptel ecosystem is the primary 100%-Elisp agentic
  stack; =gptel-agent= is a ready-made agent harness built on gptel presets
  and tools; =macher= + =macher-agent= add loops/continuations/parallel
  subagents on top of gptel.
- Non-gptel alternatives are external-CLI-bound (ACP =agent-shell=,
  =claude-code-ide.el= via Claude Code SDK/MCP) — architecturally opposed to
  Consortium's "model output is data, not authority" model; they embed a
  foreign agent runtime.

** LEM (lem-project, CL Cookbook; accessed 2026-09-20)

- =lem-project/lem=: general-purpose editor/IDE in Common Lisp, MIT, ~3k
  stars, actively maintained (repo updated Sep 2026).
- Frontends: ncurses/TUI, SDL2 (deprecated), webview; "Rooms" cloud product.
- Built-in LSP client (Python, Go, Rust, JS, ...), directory mode, vi layer,
  git mode, interactive extension in Common Lisp; sibling projects:
  =micros= (micro slime/swank), =async-process=, =webview=,
  =lem-extension-manager=.
- CL Cookbook: Lem is "tailored for Common Lisp development", swank-based
  REPL like SLIME — i.e., it can host and develop a running CL image.

* Mapping: gptel ↔ Consortium boundary

Consortium AGENTS.md: "Keep provider-specific behavior, UI concerns, and
concrete coding-agent tools outside the core workflow semantics." gptel is
exactly a provider/UI concern → it belongs at the Emacs edge; Consortium core
never depends on it.

| IDE capability                     | Substrate                                                              |
|------------------------------------+------------------------------------------------------------------------|
| Chat / rewrite / ad-hoc questions  | gptel directly (no workflow authority, no effects beyond its own tools) |
| ADARD/RAGE runs, phases, budgets   | Consortium daemon (only admitted executor); gptel *proxies* to it      |
| Fresh-context phase workers        | Consortium =start= packets; gptel supplies provider transport upstream of Prolog-RLM or is bypassed by =rlm(Provider,...)= |
| IDE tools (edit buffer, search, eval) | Elisp functions exposed as gptel tools that wrap *admitted* Consortium effects; direct-mutation tools only in non-workflow chats |
| Research artifacts (Org)           | =roam/research= convention + gptel-org properties for reproducibility   |
| Approvals / questions              | =approval_required= / =question_required= events surfaced in Emacs UI (consortium-rlm-client reducer already models them) |
| StarIntel documents/spec           | starintel-emacs tool over local JSONL corpus + lock-resolved schema (0.9.1) |

Key tension: gptel's built-in agent loop (tools fed back to the model) is
itself an agent runtime. Consortium forbids a second unrestricted runtime
inside a workflow. Resolution: two modes, explicitly separated —
(1) *workflow mode*: gptel tools are thin proxies to daemon methods
(=start/status/events/artifact/cancel=); the model proposes, Prolog decides;
(2) *free mode*: plain gptel chats with local tools, no run lineage, no
authority claims. The mode is a preset attribute, never inferred.

* LEM track decision

| Option | Description | Cost / risk | Synergy |
|--------+-------------+-------------+---------|
| A: vendor clone | Clone =lem-project/lem= into =starintel/lem= as an upstream-tracking tree (no local commits); starintel code lives beside it as a lem extension | Low; =git pull= upstream | LEM extensible in CL; star-lang/Prolog-RLM CL adapter (upstream =eba3f90=, =lisp/bridge.lisp=) can load rlm in-process |
| B: full fork | Clone with local commits, maintain a StarIntel fork | High: ~3k-star editor, active upstream, divergence tax compounds | Same, but every upstream fix is a merge |
| C: flake input | Lem as a nix flake input; no tree in the monorepo | Lowest | No in-tree hackability; does not satisfy the literal "clone repo to this mono repo" ask |
| D: none | Emacs-only IDE | Zero | Loses the CL-native track entirely |

Recommendation: *A*. It satisfies the operator's literal ask (a LEM clone
repo in the monorepo) without committing to fork maintenance (B). The
StarIntel-specific CL code goes in a separate =starintel-lem-ext= (or inside
starintel-emacs's CL dir) loaded via lem's extension mechanism at runtime —
never as commits inside =lem/= itself. The in-process synergy is real:
Consortium's Prolog-RLM boundary already has a CL bridge upstream, so a LEM
image could run ADARD phases without shelling out — but that is a later
slice, gated on the Emacs track proving the workflow model.

* Contradictions

- gptel's tool loop is an agent runtime; Consortium forbids a second
  unrestricted runtime in workflows. Resolution above (two explicit modes);
  the design phase must specify what happens when a free-mode chat touches
  workflow state (answer: it cannot — no daemon credentials/effects).
- Three Emacs clients would then exist (=consortium.el=,
  =consortium-rlm-client.el=, gptel UI). Slice 2 must collapse the first
  two before slice 3 builds on gptel; gptel is UI/transport, not a third
  client.
- LEM option B (fork) contradicts upstream-velocity reality; option A
  contradicts the user's word "clone" only superficially — a vendor clone is
  still a clone; the resolve gate should confirm A vs B explicitly.
- Operator asked to "git pull all mains" first; that sweep was aborted and
  deferred — relocations and pulls must be sequenced after this research is
  approved to avoid moving a tree mid-pull.
