#+title: Consortium
#+description: Prolog-RLM-backed orchestration for independent model workers, durable reasoning artifacts, and gated ADARD/RAGE execution.

* Consortium

Consortium is a control plane for agentic work where multiple language-model workers operate with fresh context while durable state lives outside any one model conversation.

The initial workflow is ADARD:

1. *Analyze* — establish repository state, evidence, constraints, unknowns, and a bounded problem statement.
2. *Design* — produce an implementation-ready design from the promoted analysis artifact.
3. *Adversarial Review* — independently attack the design, evidence, assumptions, security, failure modes, and testability.
4. *Resolve* — adjudicate the design and review into an explicit decision gate: approve, revise, research, or reject.
5. *Develop* — realize an approved design TDD-first.
6. *Verify* — independently verify the exact implementation head. Verification is a terminal gate, not shared-context self-review.

RAGE (Recursive Analysis with Gated Execution) is an escalation workflow that may be invoked when evidence or verification shows that another bounded analysis/design cycle is required. A local implementation defect does not automatically restart architecture research.

   |

   |

No phase worker inherits another worker's hidden chat transcript. Cross-phase knowledge must be carried through explicit artifacts, evidence references, and the durable Prolog knowledge base.

* Async harness

The harness is a persistent JSON Lines stdio process intended for Emacs
=make-process=. Starting a run admits the first Prolog-RLM Future and returns a
stable run ID without waiting for model work:

#+begin_src sh
nix run . -- --help
nix run . -- daemon --memory
#+end_src

Protocol requests have ={id, method, params}= and responses carry the same
=id=. The process also pushes ={kind:"event", event:{...}}= records. Supported
methods are =start=, =status=, =events=, =artifact=, =cancel=, =subscribe=,
=unsubscribe=, and =shutdown=.

Every phase receives a fresh session ID and one explicit packet. Consortium
submits the phase through Prolog-RLM's canonical async runtime and receives an
opaque Future; it does not own a scheduler or thread pool. Direct provider
workers use =rlm_chain:chain_invoke_async/4=. Trusted completion workers use
=rlm_completion:rlm_completion_async/4=, while deterministic fake workers use
=rlm_completion:llm_query_async/3= with an injected handler. Completion callbacks
record immutable Prolog-RLM artifacts and submit only the next admitted phase.
Cancellation revokes the current attempt fence before cancelling the active
Future, so late output cannot advance state.

Tests use deterministic =fake(...)= workers. Trusted embedding code may select
=rlm(Provider, ProviderName)= for direct provider execution or
=completion(Options)= for Prolog-RLM typed plans, tools, and subagents. Role to
model descriptors remain Consortium configuration in =consortium.toml= or the
run's =models(...)= option.

* ELLM Emacs API

ELLM is the provider-neutral Elisp conversation layer shipped with Consortium.
It keeps actors and conversation history as explicit Lisp data and delegates
provider I/O to registered backend adapters.  It does not replace the
Consortium/Prolog-RLM control plane.

#+begin_src emacs-lisp
(require 'ellm)

(ellm-defactor researcher
  :backend 'gptel
  :model "openrouter/glm-5.3-flash"
  :skills '(simple-output)
  :tools '(output-org-tree))

(let* ((request
        (ellm-ask
         'researcher
         "Explain the current input."
         :input '((document . "example"))
         :cache '(system tools messages)
         :callback
         (lambda (result error _request)
           (if error
               (message "ELLM failed: %S" error)
             (message "ELLM: %S" result)))))
       (conversation (ellm-request-conversation request)))
  ;; Later turns reuse only this explicit conversation object.
  (ellm-reply conversation "Continue."))
#+end_src

Backends implement a small async contract with =ellm-register-backend=.  Core
ELLM has no provider HTTP implementation and loads without gptel, Org-roam, or
other optional integrations.

LLM-callable tools are registered separately.  The current ELLM value is the
default =input=, while model-supplied arguments override or extend it:

#+begin_src emacs-lisp
(require 'ellm-tools)

(ellm-def-tool output-org-tree (input &key heading)
  :effect 'pure
  :description "Render INPUT as an Org tree."
  (list :heading heading :input input))

(ellm-call-tool
 'output-org-tree
 '((heading . "Recent work"))
 '((documents . ("a" "b"))))
#+end_src

Pure tools may execute locally.  Tools marked =effectful= fail closed unless an
authority bridge is installed; they do not gain local execution authority from
the model naming them.  Prompt-library adapters, gptel prompt-cache mapping,
the canonical Org tools, and the Prolog-RLM mesh bridge are separate ELLM
slices.

* Prolog-RLM runtime boundary

Consortium deliberately depends on Prolog-RLM rather than reimplementing its
generic runtime. The pinned upstream revision is tested as an ABI contract on
every =nix flake check=.

Prolog-RLM owns Futures/scheduling, providers, tools, capability narrowing,
context runtime, generic plans, skills, delegation, streaming primitives, and
the artifact store. Consortium owns ADARD/RAGE phase policy, phase packets,
workflow lineage/fencing, repair and escalation policy, exact implementation
binding, and the Consortium protocol/UI projection.

The compatibility suite in =test/prolog_rlm_contract_tests.pl= intentionally
fails when a directly consumed upstream predicate disappears or changes shape.
That keeps upstream drift visible at the integration boundary instead of
silently growing compatibility code in Consortium.

* Invariants

- Prolog owns workflow state, transition legality, budgets, authority, lineage, cancellation semantics, and durable facts.
- Models produce proposals and observations; model prose never becomes executable authority by itself.
- Every phase receives an immutable, bounded input packet.
- Every phase worker starts with fresh model context.
- Cross-phase context is explicit and inspectable.
- Design cannot begin without an analysis artifact.
- Development cannot begin without an approved resolve decision.
- Verification runs against an exact implementation identity.
- Failed verification is classified before escalation; local bugs go to bounded repair, architectural failures may re-enter ADARD/RAGE.
- No silent context sharing, silent capability widening, or unbounded recursion.
